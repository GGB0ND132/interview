# 05 人工抽查题面、候选答案与评分点

本文件由题包机械生成。12 题均为 Agent 补答，尚未人工通过。核查材料、Agent 自查与人工记录方法见 [05-human-sampling.md](05-human-sampling.md)。

## Q-0062：从使用体验看，有记忆和无记忆的 Agent 有什么区别？

主题：记忆系统；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-0062.md)

无记忆系统主要依靠本次输入，换会话往往需要重新说明偏好和背景；有记忆的系统可在授权范围内保存并召回跨轮或跨会话的信息，减少重复说明并延续任务。比如记录用户常用语言后，在新会话读取该偏好。保存记录不会更新模型权重，未召回的内容也不会自动被模型看到。记忆可能过期或记错，因此要有来源、隔离、更正和删除机制；有记忆并不保证回答正确。

评分点：

- 用同一任务对比重复说明与信息延续的体验。
- 解释保存、召回并加入上下文才影响回答。
- 说明错误记忆、过期或隐私的代价。

## Q-0419：你认为 Agent 最重要的组成部分有哪些？

主题：Agent 基础与运行循环；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-0419.md)

一种工程划分是目标与状态、模型决策、工具执行和驱动反馈的运行循环。目标规定完成条件，状态记录消息及已知结果，模型根据本轮上下文提出动作，应用验证参数和权限后执行工具，再把结果写入状态供后续判断。规划与记忆可在这些职责上扩展，不要求固定组件名称或一定使用向量库。系统还需检查预算、失败和停止条件，不能把提出工具调用等同于执行成功。

评分点：

- 说明目标、模型、工具与状态等组成及关系，接受等价划分。
- 解释执行结果回传形成闭环。
- 给出预算、失败处理或停止条件。

## Q-0883：Function Calling 与完整 Agent 有什么区别？

主题：规划、推理与任务执行；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-0883.md)

Function Calling 是模型按工具定义生成名称和结构化参数的交互能力，真正的函数由应用执行并回传结果。完整 Agent 在此之上围绕目标维护状态，根据观察选择后续行动，处理失败并判断完成或达到预算上限。一个固定流程只调用一次函数不必是 Agent；Agent 也可以通过其他动作接口执行任务。比如查天气的函数请求本身不是闭环，拿到失败后修正城市再查询并给出有依据的结果才体现动态控制。

评分点：

- 说明函数调用请求与真正执行的区别。
- 说明完整 Agent 还需状态、反馈决策及停止控制。
- 举例区分固定单次调用和动态运行循环。

## Q-0898：Coding Agent 是什么？

主题：Agent 应用架构与场景设计；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-0898.md)

Coding Agent 是面向软件任务的智能体：理解修改目标，读取仓库和相关约定，按需要编辑代码、运行构建或测试，再依据结果修正并交付。模型承担理解和决策，文件与命令工具承担真实操作，运行时保存任务状态和控制权限预算。它与只生成代码片段的助手相比多了对环境的执行和反馈；仍需核查差异、测试范围和风险，测试通过不等于所有需求都正确，也不代表代码已经部署。

评分点：

- 说明读仓库、修改、验证和根据反馈继续的闭环。
- 区分代码生成与真实工具执行。
- 说明权限、结果核验或交付限制。

## Q-1674：LLM Runtime 与 Tool Runtime 分别负责什么？

主题：Agent 基础与运行循环；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-1674.md)

LLM Runtime 在此工程划分中负责组织模型请求、传入上下文与工具定义、处理生成结果或流式事件以及模型调用预算。Tool Runtime 负责将工具请求映射到真实执行，验证参数与权限，控制超时和隔离，返回结果或可处理的错误。上层循环把结果关联到对应调用并更新状态后决定下一步。名称并非统一协议，具体系统可能合并实现；模型输出一段命令不等于工具已运行，工具成功也要核对业务结果。

评分点：

- 说明模型请求与生成处理的职责。
- 说明参数权限验证、执行和工具回执的职责。
- 解释两者通过运行循环协作，接受不同实现命名。

## Q-1675：是否所有错误都重试，参数错误如何处理？

主题：工具调用与 Function Calling；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-1675.md)

不是所有错误都应重试。临时网络故障或限流可在次数和总时限内退避重试，并尊重服务端重试提示；参数错误要先反馈字段和原因，修正参数后才重新调用。权限不足、凭证失效或业务规则拒绝应修复条件或停止，盲重试无益。有副作用操作若超时导致结果未知，先按操作 ID 查状态或用幂等键，避免重复扣款等。错误必须作为明确观察返回，不能用空结果伪装成功。

评分点：

- 区分临时故障、参数错误和权限或业务错误。
- 说明参数错误先修正、重试受次数时间限制。
- 解释结果未知时核对状态或用幂等键避免重复副作用。

## Q-2078：设计一个每天定时查天气的 Agent 框架。

主题：Agent 应用架构与场景设计；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-2078.md)

每天定时查天气通常用调度器加天气 API 的固定工作流就够了，不必强加 Agent。若还要按天气和日程动态决定建议，可让调度器创建带日期、城市和时区的任务，调用天气工具，验证时间与单位，把结果交给模型生成有依据的建议，再按授权通知用户。调度、凭证、工具执行和状态保存由应用负责；模型不自己计时。需记录上次执行、避免重复通知，设置超时与有限重试，无数据时报告缺口而非编造天气。

评分点：

- 说明定时调度与天气查询的确定性职责。
- 解释需要动态决策时模型在链路中的位置。
- 考虑时区、去重、失败或回执验证，不强求使用 Agent。

## Q-2506：ReAct 与普通单次 LLM 调用有什么区别？

主题：规划、推理与任务执行；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-2506.md)

普通单次 LLM 调用依据给定输入生成输出，通常没有应用驱动的多轮行动反馈。ReAct 让任务推理、动作和环境观察交替推进：应用执行所选工具，将回执提供给下一轮，再决定继续或回答。例如查询发现资料缺失后补查。ReAct 是一种组织方式，并不要求暴露完整内部思考，也不保证工具一定正确；仍需参数校验、预算和停止条件。单次请求也可返回工具意图，但实际执行和后续反馈由宿主承担。

评分点：

- 说明推理、行动与观察交替的结构。
- 对比单次生成与利用外部反馈继续的差异。
- 说明执行控制和结果可靠性仍由应用保障。

## Q-4836：大模型结构化输出与 Function Calling 有什么区别和联系？

主题：工具调用与 Function Calling；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-4836.md)

结构化输出让模型生成符合约定结构的内容，例如字段化的分析结果；Function Calling 则用工具名称和参数表达调用外部能力的意图，应用再执行并回传。两者都可依赖 JSON Schema 等契约，但用途不同，也不保证字段中的事实或业务参数正确。比如输出行程 JSON 只是数据，提交订单工具请求涉及真实副作用。无论使用哪种，都需处理拒答、截断、语义校验与权限；不能看到合法 JSON 就自动执行任意动作。

评分点：

- 区分结构化数据结果与工具调用意图。
- 说明应用负责工具执行，二者可共享结构契约。
- 区分结构合法与业务正确，考虑拒答或参数权限校验。

## Q-4837：Agent 记忆有哪些类型，短期、长期与情景记忆如何区分？

主题：记忆系统；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-4837.md)

短期记忆通常指当前会话或任务中的消息、状态和中间结果；长期记忆指可跨会话保留并召回的信息，如偏好或项目事实。情景记忆按内容描述发生过的事件与经历，与语义记忆的事实、程序性记忆的方法相对。生命周期和内容是不同维度，所以情景记忆也可长期保存，短期状态也可持久化以便恢复。实现可用数据库、文件或索引，关键是范围隔离、相关读取、更新和删除，而不是必须使用向量库。

评分点：

- 区分当前任务短期与跨会话长期范围。
- 说明情景记忆保存具体经历并可与长期维度交叉。
- 说明存储持久化不等于长期语义，考虑读取和维护。

## Q-7020：Context Engineering 与 RAG 是什么关系？

主题：上下文工程；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-7020.md)

上下文工程关注每次模型调用应获得哪些指令、对话状态、记忆、工具定义与观察，以及如何选择、排列和控制输入预算。RAG 是从知识来源检索相关材料供生成使用的方式，可作为上下文工程的一部分，但不涵盖全部工作。例如文档问答先检索片段，再筛选去重、保留出处并与任务指令组织成输入。更多内容不一定更好，需检查时效、权限、相关性和不可信资料中的指令，不能把检索结果直接当高优先级规则。

评分点：

- 说明上下文工程管理一次调用的整体信息。
- 解释 RAG 是资料获取途径而非上下文工程全部。
- 举例说明筛选、预算、来源或不可信内容处理。

## Q-7196：输入超过模型上下文窗口时，有哪些处理方式？

主题：上下文工程；内容版本：05.1；答案来源：agent_generated。

[固定原题](https://github.com/didilili/mianstack/blob/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77/questions/Q-7196.md)

输入超过上下文窗口时，先按任务筛掉无关重复内容，给系统指令、当前目标、关键状态及输出预留预算；长文档可分块检索相关段落，长历史可摘要并保留关键原文定位。可把中间结果存到外部按需读取，或分阶段处理再合并；确有需求时选择更大窗口的模型，但成本和注意力质量仍有限制。不能任意截断导致指令或工具调用回执不完整，摘要也会丢信息，需验证关键事实和当前任务条件没有遗失。

评分点：

- 给出筛选、检索、摘要或分阶段处理等具体方式。
- 说明为输出和关键指令状态保留预算。
- 指出摘要或截断风险与结果核对，不把大窗口当万能解。
