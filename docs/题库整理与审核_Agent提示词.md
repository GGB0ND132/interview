## 工作流程

### 1. 登记来源

为每份材料登记标题、发布方、URL 或本地文件标识、获取日期、文件 SHA-256 或 Git commit、格式、页数、许可/使用范围核对结果及 `source_id`。区分“个人本地参考”“可上传第三方服务”“可在项目中公开”三种用途；未知就写 `unknown`，不要推定网站上能阅读就能整批转载。保留原件；原始抽取文本不要覆盖原件。

**完成条件：**每道候选题都能关联到一个来源记录及可回查的页码、题号或段落。许可未确认的材料只能进入候选区。

### 2. 抽取候选题

PDF 逐页抽文本并保留页号；Word 按标题、段落、表格读取。识别题面与答案边界，处理跨页答案、页眉页脚、双栏、图片、代码缩进和表格。需要 OCR 的页标记人工核对。可以用模型辅助切分，但每条候选必须同时保存原文片段和定位；文本无法对应原件时标记 `extraction_uncertain`。不要补写原材料没有的答案。

先做近似题检测：相同考察点、不同问法可组成题族，保留各自来源；考察边界不同则保留为不同题。抽取出的候选题号是临时号，去重后再固定可读 `code`。

**完成条件：**本轮最多 30 道候选的题面、答案边界和出处可人工逐条检查；切分不确定的题列在问题清单，不进入下一步自动发布。

### 3. 生成结构化题目记录

每题至少给出以下字段，使用可被程序校验的 JSON 或仓库已采用的等价结构。`answer_json` 需要完整参考答案、必要前提、可接受的正确变体和常见误区；`rubric_json` 列出可观察的评分点，不只放一篇长答案。

```text
code, version, prompt, original_prompt, source_id, source_locator,
role_tracks, primary_competency_id, secondary_competency_ids,
content_layer, difficulty, difficulty_reason, stage, format_tags,
answer_json, rubric_json, answer_refs, review_status,
review_notes, extraction_confidence, classification_confidence
```

`source_locator` 对 PDF 至少包含页码和可核对的短原文；MianStack 至少包含固定 commit、题号和文件路径。编辑后的题面与原题分开存。来源材料中没有答案或答案存在疑点时保留候选、标记 `answer_pending`，不能为补齐字段编造标准答案。数据库主键沿用需求文档中的 UUID，`code` 只作稳定、可读题号。

**完成条件：**每条候选均能通过结构校验；缺失字段和未确定事实显式标为待审核，不能用空泛占位冒充完整内容。

### 4. 多维分类

把以下维度独立标注，不能把它们混成一棵目录树：

| 维度 | 取值规则 |
| --- | --- |
| `role_tracks` | Python 后端为本轮主方向；只有题目确实适用时才增加其他方向 |
| `primary_competency_id` | 优先复用现有能力地图 ID；Python 基础等缺口提出新 ID 建议，但不擅自宣称已发布 |
| `content_layer` | `foundation` 基础原理、`role_core` 岗位核心、`production_engineering` 生产工程、`product_topic` 产品专题 |
| `difficulty` | 技术、项目和行为题用 `easy` 基础、`medium` 进阶、`hard` 挑战；开场与反问用 `all`，表示各难度共用 |
| `stage` | `introduction`、`project`、`technical`、`behavioral`、`candidate_questions`；技术 PDF 不能硬充项目/行为题 |
| `format_tags` | 如概念解释、代码分析、场景应用、故障排查、方案权衡 |

初次标注可由规则和模型提出，但每题给出 `difficulty_reason` 和分类置信度。低置信度、多个能力都可能是主能力、岗位相关性不明确的题集中列给人工复核。

**完成条件：**每道候选只有一个主要考察能力，内容层级、难度和环节分别有依据；无法确定时保留待审状态。

## 难度判定标准

按“合格回答至少需要什么”判定，不按原文篇幅、来源标签、术语是否高级或模型能写出多长答案判定。`content_layer` 与难度相互独立。问题缺少必要条件、存在多种互斥解释时先标 `needs_clarification`，不要靠脑补把它判为挑战题。

| 难度 | 合格回答的最低要求 | 典型问法 |
| --- | --- | --- |
| 基础 `easy` | 解释一个核心概念或标准用法，给出直接例子；条件明确，通常不要求多个方案权衡 | `range` 的边界和步长；字典键视图是什么 |
| 进阶 `medium` | 把机制用于给定场景，解释原因、边界或常见错误；通常需要关联两个概念、分析一段代码或完成有限排查 | 异步接口中调用阻塞函数会怎样；某查询为何没用预期索引 |
| 挑战 `hard` | 同时处理多个约束或故障，比较可行方案的代价，说明验证与恢复方式；合格回答需要清晰的判断过程 | 并发更新下缓存与数据库如何保持可接受的一致性，失败时怎样补偿和验证 |

- 题面只问“是什么”，即使参考答案讨论了架构，也按题面所要求的最低充分答案定级；要提高难度须先经人工审核改写题面并增加约束。
- “生产工程”不自动等于挑战；一个简单的日志定位场景可以是基础或进阶。“基础原理”也可以有进阶边界题。
- 项目/行为题按所需的决策、个人行动、证据和反思深度定级，不以候选人工作年限直接定级。自我介绍和候选人反问记录 `difficulty=all`；规划器在任一难度都可选取，不复制成三道同题。
- 每题必须写一句 `difficulty_reason`，指出题面中触发该等级的具体条件。等级拿不准时给出两个候选等级及分歧点，交人工定稿。

## 审核规则

Agent 可完成第一轮检查并给出推荐结论；**只有用户或明确指定的人工审核者能把题目从候选改为 `reviewed`**。内容状态沿用 `candidate → extracted → classified → reviewed → published`；退回写原因，旧题退出使用标 `retired`。这些不是 `.scratch/` 实施问题的 triage 标签。

逐题核查：

1. **提取：**题目、答案、代码和页码与原件一致；跨页内容没有串题。
2. **来源：**来源可回查，引用确实支持题面或答案；第三方资料的许可适用于计划用途。
3. **技术：**关键结论、版本前提、反例和可接受的不同答案已核对；原 PDF 自带答案不能独立证明自己正确。
4. **岗位与难度：**能力标签和等级符合上表；基础速记题优先用于单题试题练习，模拟面试要覆盖项目和场景判断。
5. **评分：**评分点能区分完整、部分正确、错误和“不会”；项目/行为题不把未经核验的个人经历判作事实错误。

每题输出 `建议通过 / 退回修改 / 暂缓 / 不收录`、具体理由及需要用户决定的问题。审核报告按题号列出**题面、原文位置、分类与难度理由、关键评分点、发现的错误、来源/许可状态**，让用户不用通读整份 PDF 也能决策。人工确认时记录审核人、时间、题目版本和结论；修改答案、评分点或来源后重新进入审核。

**完成条件：**本批所有候选都有明确去向和可核查的审核记录；`published` 中没有待确认许可、待核技术结论或占位答案。

## 建库与导入

正式题库采用结构化源文件 + SQLite 业务表，不把 PDF/Word 或整批题目上传到百炼充当主问题池。先检查现有后端是否已有模型、迁移或导入器；若没有，按需求文档最小实现：来源清单、岗位包、能力、题目、审核记录和版本关系。代码放在项目约定的 `backend/app/content/`，运行数据放在项目数据目录；不要把运行库当唯一原始题库。

导入器依次执行：读取源文件 → JSON/字段校验 → 能力 ID 和来源定位校验 → 重复题与稳定题号检查 → 人工审核记录与许可检查 → 预览新增/变更/拒绝项 → 事务写入。`pack_questions.answer_json` 保存已审核答案，`rubric_json` 保存评分点，`answer_refs_json` 保存答案依据；题目 ID、版本、答案版本在历史会话中保持可追溯。重复导入同一版本不生成第二份记录；修改已发布题应产生新版本。

本轮即使实现导入器，也只用明确获批的题目测试发布。没有人工批准时保留候选及可执行的预览，不把候选写成正式 `published`。在发布前展示岗位、难度、环节、能力分布及题量缺口；没有足够内容时岗位包保持筹备状态。

**完成条件：**候选记录可校验和预览；获批样本能够幂等导入并按岗位、能力、难度、环节查询；未获批题无法由正式选题查询到。

## 运行调用与验收

用户选择方向或提供 JD 时，先把 JD 明示要求映射到已维护的能力 ID，再从 `published` 题过滤岗位、难度、环节、答案状态和近期已问；按岗位核心、JD 明示要求、弱项及覆盖缺口排序，在合格候选中随机。自我介绍与简历只重排尚未出示的问题和触发回答驱动的追问，不允许据此捏造新主问题或经历。正式评分使用审核答案和评分点；超出答案范围的技术结论才按需查可靠资料。知识库可辅助找原始 PDF 页或核对官方资料，但召回结果需回查原件，不能充当人工审核结论。

本批结束时提交：来源清单、候选题结构化文件、逐题审核报告、重复与错误清单、分类和难度分布、能力覆盖缺口、导入预览/实际导入结果、验证记录。分别报告“已抽取”“Agent 建议通过”“人工已审核”“已发布”数量，不合并口径。验证至少包含：一题来源和页码回查、一题难度分歧、一题有错误的参考答案、一题重复题，以及未审核题无法被正式选中。

当前前端仍为演示，后端业务服务尚未完成；不能把候选文件、导入器可运行或模型评分示例报告为完整面试功能已上线。
