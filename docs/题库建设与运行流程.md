# 题库建设与运行流程

日期：2026-11-09  
状态：实施方案，尚未完成批量抽题、正式题库入库或后端联调  
适用范围：首批 Agent 原理与系统基础档；后续分批增加 Python 后端、React/Vue 前端。与[项目架构与需求 V1.5](项目架构与需求_V1.md)中的模拟面试和试题练习配套。

交给其他 Agent 批量整理时使用[题库整理与审核 Agent 提示词](题库整理与审核_Agent提示词.md)。

## 1. 最终要得到什么

正式练习的主问题来自**本地结构化、通过发布校验的题库**。首批批量导入 MianStack `questions/` 的 Agent 基础题，按主题抽查；这不等于每题经过人工技术核对。PDF、Word、MianStack 等是取材来源；JD 是岗位能力匹配依据；简历和自我介绍是个人情境；技术知识库是可选的资料查找与事实核对工具。四者不混在同一个检索库里。

```text
原始 PDF / Word / MianStack
    → 来源登记 → 提取候选题和答案 → 切分复核 → 多维标注
    → 逐题自动校验 → 分主题人工抽查 → 发布到结构化题库
    → 按岗位/JD/模式筛选与编排 → 用户回答 → 有边界地追问与评价
```

原始资料不直接作为运行时随机出题池；也不要求把每道题上传到百炼。单次上传数量、知识库容量和解析接口配额是不同约束，不决定题库的数据结构。

## 2. 来源登记和使用边界

每份材料先建来源记录，再抽题。至少登记 `source_id`、标题、来源类型、原始 URL 或本地文件标识、作者/发布方、获取日期、文件 SHA-256、版本或 Git commit、许可核对结论、允许的用途。题目引用 `source_id` 和精确定位，不把下载路径当永久出处。

| 来源 | 候选内容 | 定位方式 | 注意事项 |
| --- | --- | --- | --- |
| PDF | 题面、答案、代码示例 | 文件哈希 + 页码 + 原文片段；必要时记页内位置 | 跨页答案、页眉页脚、双栏、扫描页和代码缩进可能切错 |
| DOCX / DOC | 标题、段落、列表、表格中的题目与答案 | 文件哈希 + 标题/段落或表格位置 + 原文片段 | DOC 先用可靠解析或转换工具；不要只改后缀 |
| MianStack | 标准题、已有答案、分类元数据 | 固定 commit + 题号 + 文件路径/URL | `answerStatus` 不等于全部题都有答案；第三方面经/题集另核许可；网站关联数据不全在公开仓库 |
| 自编题 / 真实 JD | 岗位场景、项目问题、行为问题 | 编写记录；JD 另存原文片段 | JD 只说明岗位要求，不能证明技术答案正确 |

个人本地参考、上传到第三方云、在项目中公开原题和答案属于不同使用方式。材料来源不清或许可未核对时先留在候选区；公开发布或上传第三方服务前核对权利范围。MianStack 自有题解的许可不能延伸到其收录的第三方面经与题集。

## 3. 从 PDF / Word 到一题一记录

这里的“一题一记录”是**最终数据形式**，不是要求逐字手工录入整本 PDF。

1. **逐页/逐段提取。** PDF 保留页码与文本顺序；DOCX 保留标题、段落和表格结构；扫描页或图片中的文字单独 OCR，并标记需要人工核图。原文件和提取文本都保留，不直接覆盖。
2. **候选切分。** 按问句、标题和答案段落识别题目边界，允许答案跨页。模型可辅助输出结构化候选，但必须给出源页和原文片段；不得把模型补写答案伪称为原文答案。首批 MianStack 无答案题允许 Agent 补写候选答案，并单独记录 `answer_origin=agent_generated`、生成时间、模型和版本。
3. **切分复核。** 检查题面是否完整、答案是否串入下一题、代码/公式是否保真、页码是否正确。无法可靠切分的题标记待人工处理，不让其进入发布队列。
4. **去重与合并。** 归一化标题后找相同或近似题；同一考察点的不同问法可保留为一个题族，但各来源与问法分别记录。不要仅靠文本相似度把考察边界不同的题合并。
5. **批量建议标签。** 规则和模型给出岗位、能力、内容层级、难度、环节及置信度；人工确认分类体系、低置信度项和待发布题。无需对每条候选从零手选全部标签。

例如已抽查的 Python PDF 第 1 页有 `range` 题，可先生成以下**候选**记录。示例评分点只作为编辑起点，不代表该 PDF 的整本答案已经审核：

```json
{
  "code": "Q-PY-0001",
  "prompt": "Python 的 range 如何使用？请举例说明。",
  "role_tracks": ["python_backend"],
  "competency_ids": ["python_iteration"],
  "content_layer": "foundation",
  "difficulty": "easy",
  "stage": "technical",
  "answer": "待编辑核对的参考答案",
  "rubric": ["起止边界", "步长", "返回对象及迭代使用", "恰当示例"],
  "source": {"source_id": "SRC-PY-PDF-01", "pages": [1, 2], "excerpt": "Python 的 range 函数如何运用？请举例说明"},
  "review_status": "candidate",
  "version": 1
}
```

生产数据中 `answer` 必须填入完整正文或指向不可变的答案版本，并记录原题答案或 Agent 补答的来源状态；`source.excerpt` 必须与原文核对。`code` 是供编辑和追溯的稳定题号；导入现有业务表时另分配 UUID 作为数据库主键。题号只在去重后固定，不能每次抽取重新编号。若 PDF 提取文字出现错字，应同时保留原文和编辑后的题面，不伪称编辑文本是原文逐字引用。

## 4. 多维分类，不做单一目录树

“基础原理 → 核心能力 → 生产工程 → 产品专题”作为 `content_layer`，描述题目在准备路线中的位置；岗位、能力、难度和面试环节是独立字段。同题可以适用多个岗位，但每道题应有一个主要考察能力，其他能力作为辅助标签。

| 维度 | 用途 | 示例 |
| --- | --- | --- |
| 岗位方向 `role_tracks` | 限定候选池 | Agent 原理与系统、Python 后端、React 前端、Vue 前端 |
| 能力 `competency_ids` | 对齐 JD 和历史弱项 | Python 迭代、接口鉴权、MySQL 索引、Agent 工具调用 |
| 内容层级 `content_layer` | 控制知识覆盖 | 基础原理、岗位核心、生产工程、产品专题 |
| 难度 `difficulty` | 控制深度；开场和反问跨难度共用 | 基础、进阶、挑战、跨难度 `all` |
| 环节 `stage` | 编排真实面试 | 自我介绍、项目/经历、技术、行为、候选人反问 |
| 问法 `format_tags` | 避免一场全是定义题 | 概念解释、代码分析、故障排查、方案权衡 |

能力 ID 从[能力地图](content-baseline/能力地图.md)维护，JD 中的原文要求映射到这些 ID；不能因 JD 出现一个新词就临时创建已发布能力或未经审核的新题。内容层级不是难度：基础原理也可以有较难的边界题，生产工程也可以有入门场景题。

## 5. 审核和发布

候选状态建议为 `candidate → extracted → classified → validated → published`；`validated` 表示逐题自动校验通过，不代表人工核对过技术结论。另存 `human_sample_reviewed` 和抽查记录；问题退回时记录原因，失效题使用 `retired`，不原位删改历史版本。这是**题库内容状态**，不替代 `.scratch/` 中实施问题的五种 triage 状态。

| 审核关口 | 必须检查 | 不通过时 |
| --- | --- | --- |
| 提取准确 | 题面/答案边界、页码、代码、表格及原文片段一致 | 修正切分或留在候选区 |
| 岗位适配 | 对应真实能力，难度与环节合理；不靠过量基础小题凑模拟面试 | 重标、改写并留改写记录，或只用于试题练习 |
| 答案可评分 | 每题有非占位答案、可接受变体、评分点和答案来源状态；抽查题核对关键结论，争议题补查独立依据 | 缺字段或占位内容不得评分；抽查发现错题先停用该题并扩大同主题抽查 |
| 评分可用 | 有明确考察点、必须点、可选点和常见误区；非技术题有适用的表达标准 | 补评分表，不能只存一篇长答案 |
| 来源与权利 | 来源可回查，许可与拟使用方式匹配 | 仅作本地参考或停止导入 |

首批 Agent 基础档每个主题发布前人工抽查 2 题，优先包含 Agent 补答题，记录审核人、时间、版本、核对资料、发现问题和处理结果。抽查不能证明同主题其余题的答案正确；这些题仍可显示正式训练分数，项目接受此评分风险。抽查发现参考答案或评分点错误时先停用错题并扩大同主题抽查；重复发现同类错误时暂停该主题评分，修正后复查。评分页允许用户反馈题目或评分有误，保存题目 ID、答案版本和说明供复核。技术题用“完整、部分正确、错误、明确不会”样本试答；项目/行为题检查“经历不足、贡献不清、没有量化指标”时反馈是否公平。模型评分与人工判断冲突时复核答案和评分表，再决定修正内容或评价策略。

## 6. 发布入库与版本

题库的权威内容建议保存在可审查的结构化源文件中，发布时导入项目业务数据库的 `role_packs`、`pack_competencies`、`pack_questions` 等表。业务数据库负责按字段筛选、版本快照、历史和去重；百炼知识库不是题库主存储。

发布工具按以下顺序执行：读取源文件 → 逐题检查题面、分类/难度、完整答案与评分点、原题定位、答案来源状态和唯一 ID → 去重及权利检查 → 核对每主题 2 题的抽查记录 → 预览新增、可评分数和拒绝项 → 事务导入通过项 → 更新岗位包版本。单题校验失败时该题不可评分，不拖累其他通过项；发布前显示实际可用题数。相同版本重复导入应得到相同结果；已发布题目、答案或评分点变化时创建新版本，历史会话仍引用旧版本。

参考答案正文、可接受的不同答法及 `answer_origin` 保存在版本化 `pack_questions.answer_json`；`answer_refs_json` 只保存实际核对过且支持相应结论的独立资料引用。MianStack 原题定位单独保存在题目来源，不能冒充独立技术依据。没有独立资料的题仍可参与训练评分，但不得展示虚构的资料引用。题目 ID 与版本确定唯一答案和评分表版本，历史会话保留当时快照。

首批取材基线为 MianStack 提交 [`b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77`](https://github.com/didilili/mianstack/tree/b1e033dd72db1d4e23fa0c5b8d0ae28fd330de77)；该提交的 Agent 基础题盘点为 115 道，其中 30 道标记已有答案、85 道标记待补答案。这是取材目标，不是已导入或已核对数量；实际可评分数以逐题校验通过数为准。另从通用职业题与自编题中准备少量开场、经历或假设情境、行为和反问题及各环节反馈标准，允许跨场次复用。模拟面试只从适合追问和覆盖能力的技术题中选；试题练习可使用全部合格基础技术题。旧清单中的“每难度 25 题”是长期扩容预算，不是当前开放门槛。

## 7. 运行时怎么调用

1. 用户从模拟面试或试题练习的独立入口选择岗位方向与难度。服务端读取**已发布题库**；首批为 Agent 原理与系统基础档。模拟面试没有 JD 时按基础能力随机选题，有 JD 时提高已确认且可映射主题的权重；简历确认后的项目与职责用于经历切入和追问，仍视为用户陈述。其他方向只在各自内容与评分表通过发布门槛后开放。
2. `availability` 分别检查模拟面试的必需环节与本场优先能力可覆盖性、试题练习的候选池非空。JD 要求无相关合格题时显示缺口；用户仍可继续练其他能力，报告保留未覆盖项。不临时生成主问题填空。
3. 模拟面试规划器先过滤 `published`、岗位、难度、环节、答案可用性、面试适用性及近期已问；首批在题量足够的主题中带权随机选 3～4 个，JD 可提高相关主题权重，保存随机结果。每组后更新 `unobserved / insufficient / observed / not_applicable` 状态；仅在必需环节和优先能力获得足够评价证据后完整结束。答错或明确不会是可评价证据；空白提交只记 0 分，仍为证据不足。用户结束、保护上限、题池耗尽或关键证据未补足时生成说明缺口的部分报告。首批一般约 7～8 道主问题，上限 12 道。
4. 模拟面试先给已发布的自我介绍题。用户回答后可提取其明确提到的项目、技术和职责，重排后续**尚未出示**的候选题；简历解析结果经用户查看确认后提供额外情境。没有简历时也能练；没有实际项目经历时走明确的假设情境分支。用户确认简历只表示允许用这些陈述追问，不等于经历真实性已由外部核验。
5. 试题练习按岗位、能力、难度和题型过滤已发布且可评价的题目；从合格池随机抽一道，优先排除近期已做题，题池不足则明确允许重复或提示无题。保存候选池快照、随机种子、题目 ID 和版本。回答后立即给本题反馈；重答生成关联的新尝试，不改写旧答案，下一题重新抽样。
6. 主问题直接呈现已发布题面。模拟面试针对用户回答及已确认 JD/简历可提出一条聚焦的澄清或深挖追问，受当前主问题、难度和次数上限约束；没有相关主问题的 JD 要求不靠追问伪装为已覆盖。模型不能凭空生成新的正式主问题。试题练习默认无追问。
7. 非空回答评价时提供该题的答案版本、评分要点和本组问答，按语义覆盖与事实判断评分，不做逐字相似度比较。首批未逐题核实的 Agent 补答题仍可给训练分数；技术结论超出答案范围或存在版本争议时才调用外部资料核对，无依据时不作确定的新增技术判断，也不伪造引用。空白提交由后端直接记 0 分、计入均分并单列，不调用模型。模拟面试整场结束后公开详细反馈；试题练习每题即时反馈。

现有接口顺序可沿用 `GET /role-packs` → `POST /role-packs/{id}/availability` → `POST /sessions` → `POST /sessions/{id}/start` → `POST /sessions/{id}/answers` → `POST /sessions/{id}/next`。上表是**目标流程**，当前 `fronted/` 仍是演示数据，后端业务服务尚未实现。

## 8. 知识库什么时候参与

| 场景 | 是否需要检索 | 可靠判断依据 |
| --- | --- | --- |
| 找 PDF/Word 中某题原文 | 可选；知识库适合语义发现 | 最终回查原文件哈希、页码和原文片段；相似召回不等于精确出处 |
| 审核题目的技术答案 | 可选；官方文档检索有价值 | 官方资料或可靠技术资料；原题 PDF 自己的答案不能独立证明自己正确 |
| 从已发布题库选主问题 | 不需要 | 结构化字段、审核状态和选题规则 |
| 评价题库答案已覆盖的内容 | 通常不需要 | 版本化答案与来源状态 + 评分要点 + 用户回答 |
| 处理超出标准答案的技术追问或新版本变化 | 按需检索 | 有效资料片段；没有直接依据则不作确定结论 |
| 按个人 JD、简历或自我介绍选题 | 通常不需要上传百炼 | 用户确认的能力映射及本场回答；个人自述不作技术事实依据 |

若使用百炼检索，建议把“原始题库资料查找”和“可靠技术依据”区分用途，避免用同一份题解既出题又证明自己的答案。题库全文不作为运行时评分检索源，防止答案泄漏、错召回和额外费用。现有 11 篇系统技术资料可以保留作技术核对试点，但不要求随着题量一比一增加文档。

## 9. 第一批执行顺序与验收

1. 固定首批“Agent 原理与系统”基础档的能力 ID 与分类词表；Python 后端和 React/Vue 后续分批建设。
2. 固定 MianStack 提交，只批量提取 `questions/` 中的 115 道 Agent 基础题；记录原题 ID、文件路径、许可和答案状态。缺答案题由 Agent 补写并留生成来源，不导入 `collections/` 或第三方面经。
3. 逐题做字段、答案、评分点、来源定位和重复 ID 校验；每个主题发布前人工抽查 2 题，优先覆盖补答题，发现错误按第 5 节停用、扩大抽查和复查。
4. 做版本化导入，只发布校验通过项，显示实际可评分题数；另准备可跨场次复用的通用环节题与评分标准。
